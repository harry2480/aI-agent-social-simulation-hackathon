# SLEEP CITY 2.0 テストガイドライン

このドキュメントは、SLEEP CITY 2.0 におけるテストの書き方・運用方法をまとめたガイドラインです。
基本ルールは `CLAUDE.md` および `docs/品質チェック・テスト規約.md` にも記載しています。

Simulation Engine は「同一 Seed・同一 Config なら同一結果」であることが要件（要件定義 44 章 再現性）のため、
テストの最重要ターゲットは **domain 層の決定論的ロジック**です。

## テストの種類と構成

プロジェクトでは以下の種類のテストを運用します（プロジェクトのフェーズに合わせて段階的に導入します）。

| 種類 | 配置場所 | 実行環境 | 実行コマンド | 用途 | 状態 |
|------|----------|----------|-------------|------|------|
| ユニットテスト | `apps/webapp/test/unit/` | Vitest | `pnpm test:unit` | domain（Simulation Engine・Sleep / Fatigue・Rs・Cascade 判定）と application（UseCase） | 導入済み |
| Integration テスト | `apps/webapp/test/integration/` | Vitest + Node.js | `pnpm test:integration` | infrastructure（Prisma Repository・OpenRouter Adapter） | 導入済み（`INTEGRATION_TEST=true` + `DATABASE_URL` 必須） |
| 再現性テスト | `apps/webapp/test/unit/domain/services/` | Vitest | `pnpm test:unit` | 同一 Seed で Run 結果が一致することの検証 | P0 で導入 |
| E2Eテスト | `apps/webapp/test/e2e/` | Playwright | `pnpm test:e2e` | Simulation 起動 → City Map 表示 → Causal Graph 参照のフロー検証 | 未導入（P2） |

テストディレクトリはソース構造を mirror します（`src/backend/domain/services/sleep.service.ts` →
`test/unit/domain/services/sleep.service.test.ts`）。

## CI実行フロー

PR が作成されると、`.github/workflows/verify.yml` で以下が順次実行されます。

```text
PR Created / Push to main
  └── verify
      ├── pnpm lint            （Biome によるフォーマット + lint）
      ├── prisma generate      （Prisma Client 型生成）
      ├── pnpm typecheck       （TypeScript 型チェック）
      ├── pnpm test:unit       （Vitest ユニットテスト）
      └── pnpm depcruise       （依存方向チェック）
```

全ステップがパスするとマージ可能になります。
Integration テストは `DATABASE_URL` が設定された環境でのみ実行し、未設定時は自動スキップします。

## ユニットテスト

### 対象
- domain 層の Simulation ロジック（`domain/models/`、`domain/services/`）
- application 層の UseCase（Gateway はモックを注入）
- Sleep Debt 計算、Fatigue / Stress 更新、確率イベントの抽選、Causal Edge 構築、
  Sleep Transmission 判定、Rs 算出、Cascade 判定、Intervention 適用

### 配置ルール
`test/unit/` 配下に、ソース構造を mirror して `*.test.ts` として配置します。

```text
apps/webapp/test/unit/
├── domain/
│   ├── models/
│   │   ├── agent.model.test.ts
│   │   └── sleep-state.model.test.ts
│   └── services/
│       ├── sleep.service.test.ts
│       ├── reproduction-number.service.test.ts
│       └── cascade.service.test.ts
└── application/
    └── usecases/
        └── run-simulation.usecase.test.ts
```

### ポイント
- **mock は極力使わない**: Simulation ロジックは純粋関数 / 純粋なクラスとして切り出したうえでテストする。
- **乱数は Seed 固定で扱う**: `SeededRandomService` に固定 Seed を渡す。`Math.random()` に依存したコードはテスト不能とみなし、リファクタリング対象とする。
- **時刻は Simulation Clock を注入する**: `Date.now()` への依存を作らない。
- **外部 API は DI でモックする**: OpenRouter などの外部 API クライアントは `AiDecisionGateway` interface 越しに Fake/Mock 実装へ差し替える。
- **DB は unit では触らない**: Repository は interface のインメモリ実装（Fake）で差し替える。

### 再現性テストの書き方
同一 Config・同一 Seed で 2 回 Run し、KPI と Event 列が一致することを検証します。

```typescript
const config = { seed: 42, population: 50, days: 2, initialSleepDeprivedRate: 0.05 };

const runA = await simulationEngine.run(config);
const runB = await simulationEngine.run(config);

expect(runB.metrics).toEqual(runA.metrics);
expect(runB.events.map((e) => e.type)).toEqual(runA.events.map((e) => e.type));
```

AI Decision を有効にした Run は非決定になり得るため、再現性テストでは Rule-based Adapter か
Decision Cache を注入した状態で検証します。

## Integration テスト

### 対象
- Prisma Repository（experiments / simulation_runs / agents / events / causal_edges / metrics などの永続化）
- OpenRouter Adapter（Structured Output のパース、形式不正時の挙動）

### 前提
- ローカル DB が起動していること（`pnpm supabase start`）
- マイグレーション適用済みであること（`pnpm db:migrate`）
- `INTEGRATION_TEST=true` と `DATABASE_URL` が設定されていること（未設定ならテストはスキップ）

### 設計原則
#### 1. 依存関係（DB クライアント等）を DI する
Repository はコンストラクタで Prisma Client を受け取り、テストではテスト用インスタンスを注入する。

#### 2. 外部 API は Fake で差し替える
OpenRouter との通信部分は原則 Fake レスポンスで検証する。実 API を叩くテストは既定でスキップし、
明示的なフラグを立てたときのみ実行する（Rate Limit とコストを避けるため）。

#### 3. DB 状態を必ず検証する（最重要）
**関数の戻り値だけでなく、DB の状態を必ず検証する。**

```typescript
const result = await simulationRunRepository.save(run);
expect(result.id).toBeDefined();

const saved = await prisma.simulationRun.findUnique({ where: { id: result.id } });
expect(saved?.status).toBe("completed");
expect(saved?.peakRs).toBeCloseTo(1.34, 2);
```

#### 4. エラーケースの DB 状態検証
Event 保存に失敗した場合に、Causal Edge や Metrics が中途半端に残らないことをトランザクション単位で確認する。

#### 5. クリーンアップを徹底する
テストで作成した Simulation Run / Event は `afterEach` で必ず削除する。
Run 単位で削除できるよう、テストデータは必ず一意な Run ID の下にぶら下げる。

## E2E テスト（未導入 / P2）

### 対象
- Simulation 作成 → Watch Mode 実行 → City Map 上での状態遷移確認
- Agent クリック → Agent Detail 表示 → Causal Graph で親 Event へ遡る導線
- Experiment 実行 → Experiment Dashboard での比較表示

### 設計方針
- Playwright を使用
- Simulation は小規模 Population・短期間・Seed 固定で実行し、実行時間を抑える
- AI Decision は Rule-based Adapter に固定し、非決定性を排除する
- CI ではアプリケーションのビルド後に実行

## テスト作成時の注意事項

### テスト追加が必要なケース
以下のケースではテスト追加が必須です：
- Sleep Debt / Fatigue / Stress の計算式の変更
- Rs・Cascade Reach・Cascade 判定条件の変更
- 確率イベント（事故・作業ミス）の乗算モデルの変更
- Sleep Transmission の判定条件（Sleep Opportunity Loss ≥ 30 分など）の変更
- Intervention の適用ロジックの追加・変更

加えて、以下のケースでもテスト追加を推奨します：
- 新しいユーティリティ関数の追加
- 既存ロジックのリファクタリング（回帰テストとして）
- バグ修正（再発防止テストとして）

### 閾値はテストにハードコードしない
睡眠状態や Cascade の閾値は Experiment Config から変更可能な仕様のため、
テスト側も Config を明示的に渡し、既定値に暗黙依存しないようにします。

### describe/it の構造化
関連するケースは `describe` でグループ化し、意図を明確にします。
境界値（Sleep Debt = 1h / 2h / 5h、Rs = 1.0、Cascade Reach = Population の 10%）は必ず個別ケースとして書きます。

### 一意性の確保
Integration テストのレコード ID には Run 単位の UUID を含めて、並列実行時の重複・コンフリクトを防止します。
一方、domain の Unit テストでは ID を固定値にし、再現性を優先します。
