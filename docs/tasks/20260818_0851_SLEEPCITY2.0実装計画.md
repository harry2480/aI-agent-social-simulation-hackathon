## 1. 目的

**開発者・研究者が「睡眠不足が都市の中で自己増殖し始める条件を、事前予測なしに発見できる状態」になるため。**

既知の「寝不足だと事故が増える」という関係を可視化することが目的ではない。
複数の AI Agent と都市 Network を相互作用させ、以下の問いに対して定量的な結果と因果経路を提示できる状態を作る。

- Sleep Cascade が継続的に拡大する条件は存在するか
- 睡眠不足が自己増殖し始める臨界点は存在するか
- どの人物・職業・ネットワーク構造が伝播を増幅するか
- どの介入施策が Sleep Cascade を抑制するか
- AI エージェントの意思決定が都市全体の創発現象にどの程度影響するか

現実都市を予測するシステムではなく、**仮説検証のための仮想実験環境**として設計する。

## 3. 設計上の重要判断

### 3.1 実行方式: ハイブリッド

672 Tick（300 Agent × 7 日 × 1 Tick 15 分）の処理を、モードごとに実行場所を分ける。

| モード | 実行場所 | 目的 |
|---|---|---|
| Watch Mode | ブラウザ（Client Component 内で Engine を駆動） | City Map をリアルタイム描画し、1x / 4x / 8x で観察・デモする |
| Experiment Mode | Node 側（ローカル `tsx` スクリプト） | Multi-seed / Sweep / Batch を描画なしで大量実行し、結果のみ永続化する |

**この分割が成立する前提**: domain 層は環境非依存の純粋 TypeScript であること。
domain 層に Prisma・Node API・`fetch`・DOM API を持ち込まない。乱数は `SeededRandomService`、時刻は Simulation Clock から取得する。

Watch Mode の実行詳細:

- Engine は Web Worker 上で実行し、描画スレッドと分離する。8x 再生時に Tick 処理が UI 操作を阻害しないため
- Run 中の状態（Agent・Event・KPI）はブラウザ内メモリを一次ソースとし、UI はそれを直接参照する
- 永続化はブラウザから Prisma を呼べないため、**Server Action 経由**で行う。Tick ごとには送らず、
  日次チェックポイントと Run 終了時に、Run サマリ・重要 Event・Causal Edge をまとめて送信する

### 3.2 フロントエンドから Engine を駆動するための境界

`.dependency-cruiser.cjs` の `frontend-only-depend-on-presentation` により、`src/frontend/` と `src/app/` は
`src/backend/presentation/` 以外を import できない。Watch Mode でクライアントが Engine を動かすために、
**ルールを緩めるのではなく、composition に client 用の組み立て口を 1 本設ける**。

- `presentation/composition/watch-mode-engine.composition.ts` が Engine を組み立てて返す
- クライアントはこの composition のみを import する。domain / infrastructure を直接触らない
- この composition は Prisma・Node 専用モジュールを一切参照しない（クライアントバンドルへ流出させないため）
- 「どこから domain がクライアントへ露出しているか」がこの 1 ファイルに集約され、追跡可能になる

**検討した代替案**: Engine を `packages/simulation-core` として workspace パッケージに切り出す案。
層構造がフラットになり Engine が domain 層から外れるため、要件が増えるまでは採用しない。

### 3.3 ブラウザから OpenRouter を直接呼ばない

`OPENROUTER_API_KEY` をクライアントへ露出させない。Watch Mode の AI Decision は
`POST /api/agents/decision`（Route Handler）を経由する。

- クライアント側に注入する Gateway 実装: HTTP 経由で Route Handler を叩く adapter
- Route Handler は composition から UseCase を取得して呼ぶだけとし、ロジックを持たない
- Node 側（Experiment Mode）では OpenRouter Adapter を直接注入する

### 3.4 API Route の扱い

本プロジェクトは loaders + Server Actions を原則とするが、要件定義 41 章の外部連携用エンドポイント
（`POST /api/simulations`、`GET /api/simulations/:id`、`POST /api/agents/decision`、`POST /api/experiments`、
`GET /api/experiments/:id`）は Batch Runner や外部スクリプトからの呼び出しを受けるため API Route を使う。
いずれも composition 経由で UseCase を呼ぶだけに留める。

ただし重い Batch（Multi-seed / Sweep / Super-spreader Stage 1）を Route Handler 上で完走させない。
Vercel Function の実行時間上限に当たるため（[docs/インフラストラクチャ規約.md](../インフラストラクチャ規約.md)）、
`POST /api/experiments` は実験の登録のみを行い、実行はローカルの `tsx` スクリプト
（`apps/webapp/scripts/run-experiment.ts`）が担い、結果のみ DB へ保存する。
Route Handler が同期実行してよいのは小規模な単発 Run に限る。

## 5. ドメインモデル設計

### 5.1 Agent

要件定義 7 章のデータモデルに準拠する。Rich Domain Model とし、以下をモデル自身の責務とする。

- `Agent.create()`: Seed 付き乱数から sleepNeed（6.5〜8.5 時間）と性格パラメータを生成し、範囲を検証する
- 属性範囲の強制: fatigue / stress は 0〜100、responsibility / riskTolerance / cooperativeness / workPressure / familyResponsibility は 0〜1
- Parent は独立職業ではなく `familyResponsibility` を持つ属性として他職種と併用する

標準 Population 300 人の職種構成は要件定義 6 章の参考構成に従い、ExperimentConfig から比率を変更可能にする。

### 5.2 Sleep / SleepState

- `Daily Sleep Deficit = max(0, Sleep Need - Actual Sleep)`
- `Sleep Debt(t+1) = Sleep Debt(t) + Daily Sleep Deficit - Recovery`
- 状態判定は `SleepState.from(sleepDebt, thresholds)` に閉じる。閾値（1h / 2h / 5h）は ExperimentConfig から上書き可能

### 5.3 SimulationEvent / CausalEdge

要件定義 20 章のモデルに準拠する。因果登録は **時間的な前後関係では行わない**（要件定義 21 章）。
Event A を Event B の原因として登録できるのは以下を満たす場合に限る。

- Event B の計算処理が Event A の出力値を参照している
- Event A がなければ Event B が発生しない、または影響量が変化する
- AI の自然言語による説明だけを因果判定に利用しない

これを保証するため、Engine 内の各処理は「参照した入力 Event の ID」を明示的に受け渡し、
CausalEdge はその受け渡し経路からのみ生成する。

## 6. Simulation Engine 設計

### 6.1 Tick 処理順

要件定義 11 章の順序を固定する。順序変更は再現性を壊すため、変更時は再現性テストの更新を伴う。

```text
時刻更新 → Scheduled Action 決定 → 移動処理 → Work / Household 処理
→ Fatigue / Stress 更新 → Decision Trigger 判定 → 必要時のみ AI Decision
→ 確率イベント判定 → Event Impact 伝播 → Sleep / Sleep Debt 更新
→ Event 保存 → Causal Edge 保存 → Sleep Transmission 判定 → KPI 更新
```

同一 Tick 内の無限連鎖を防ぐため、Event 伝播 Depth を `MAX_EVENT_DEPTH = 10` で打ち切る。

### 6.2 確率イベント

事故・作業ミスは AI ではなく Engine が算出する。

```text
Event Probability = Base × Fatigue Multiplier × Stress Multiplier
                          × Environment Multiplier × Action Multiplier
```

AI は「事故を起こすか」ではなく「事故リスクのある行動を取るか」を決める。
`continue_driving` が選ばれた場合にのみ事故抽選を行う。

### 6.3 決定論性

- 乱数は Run 単位の Seed から派生させ、用途別（Agent 生成 / 確率イベント / スケジュール揺らぎ）に独立ストリームを持つ。
  用途をまたいで同一ストリームを共有すると、機能追加のたびに過去 Run が再現できなくなるため
- Agent の反復処理順は ID 昇順で固定する。Map / Set の列挙順に依存しない
- AI Decision は非決定要因となるため、再現性検証は Rule-based Adapter または Decision Cache 有効時に行う

## 7. 伝播・指標の設計

### 7.1 Sleep Transmission

他 Agent 由来の Causal Chain によって `Sleep Opportunity Loss >= 30 分` が発生した場合に候補として記録する。
そのうち `Normal / Tired → Sleep Deprived` へ遷移したものを **New Sleep-Deprived Case** とする。
Sleep Loss と New Case は別指標として扱う。

### 7.2 Rs（Sleep Reproduction Number）

- 個人単位: `Individual Rs(A) = A が原因となった新規 Sleep-Deprived Agent 数`
- Generation 単位: `Rs(g) = Generation g が発生させた次 Generation の新規ケース数 / Generation g の Agent 数`
- UI では Current / Peak / Average Rs を表示し、**疫学上の R0 ではない旨を UI 上に常設**する

### 7.3 Cascade 判定

`Rs > 1 が 2 Generation 以上継続` かつ `Cascade Reach >= Population の 10%` を満たした場合に Cascade 発生とする。
閾値は ExperimentConfig から変更可能にする。

## 8. AI Decision 設計

詳細な実装手順は [docs/実装計画.md](../実装計画.md)（AI Agent Decision 機能）に定義済み。本計画では位置付けのみ示す。

- AI は意味的な意思決定のみ担当する。事故発生・移動時間・渋滞計算・Sleep Debt・Fatigue・作業速度・Cascade 判定・確率計算は Engine の責務
- 提示された actions からの選択のみ許可し、自由な action 生成は禁止する（Structured Output のスキーマで enum 制約）
- 全 Agent を毎 Tick 推論させない。Decision Trigger 発生時のみ呼ぶ
- Decision Context をビニング正規化した Cache キーで結果を再利用する
- OpenRouter 障害時・レスポンス形式不正時は Rule-based Fallback へ切り替え、Run を止めない
- モデル ID は `AI_MODEL` から読み、ソースへ固定しない

## 9. データモデル

要件定義 43 章のテーブル 9 種を採用する。Prisma スキーマ（`apps/webapp/prisma/schema.prisma`）へ追加する。

| テーブル | 役割 | 主な関連 |
|---|---|---|
| `experiments` | 実験定義（条件セット、Seed 群、Intervention） | → `simulation_runs` |
| `simulation_runs` | 単一 Run のメタ情報と結果サマリ | ← `experiments` / → `events`, `metrics` |
| `agents` | Run 内の Agent 属性スナップショット | ← `simulation_runs` |
| `agent_relationships` | 家族・上司部下・同僚などの関係 | ← `agents` |
| `events` | 重要 Event | ← `simulation_runs` |
| `causal_edges` | Event 間の因果エッジ | ← `events` |
| `agent_decisions` | AI / Rule-based の判断結果と理由 | ← `agents`, `events` |
| `metrics` | サンプリング間隔ごとの KPI 時系列 | ← `simulation_runs` |
| `experiment_results` | Run 横断の集計（Cascade Probability、平均・分散） | ← `experiments` |

書き込み方針:

- Tick ごとの全 Agent 状態は保存しない。重要 Event・Causal Edge・集計 Metrics・AI Decision のみ永続化する
- Metrics はサンプリング間隔（既定 1 時間 = 4 Tick）で保存する
- Event / Causal Edge はバルク Insert する。1 件ずつの `create` をループで呼ばない
- Run 単位の保存はトランザクションで囲む
- `experiments → simulation_runs → events / metrics` のカスケード削除を設定し、再実行とテストのクリーンアップに使う

既存の `Joke` モデルおよび `jokes` テーブルは Product Starter のサンプルであり、本実装では使用しない。

## 13. 実装ステップ

依存関係に沿った順序で示す。各ステップ完了時に `pnpm verify` が全パスすることを条件とする。

### Step 1: 基盤
Seeded RNG、Simulation Clock、Agent モデル、City モデル（住宅地区 2〜3 / オフィス 1〜2 / 商業 1 / 物流拠点 1 / 道路 20〜40）、ExperimentConfig。
Prisma スキーマへ 9 テーブルを追加しマイグレーションを作成する。

### Step 2: 生活サイクル
Sleep / Sleep Debt / Recovery、Fatigue・Stress、Schedule、Work。
Sleep Debt が日単位で蓄積・回復することを Unit テストで確認する。

### Step 3: 交通と労働の連鎖
Commute、Driver、Accident、Traffic Jam、Overtime。
**このステップの完了条件: LLM なしで、一人の睡眠不足が Causal Chain（Driver → Accident → Traffic Jam →
Late Arrival → Overtime → Sleep Loss）を通じて複数 Agent の睡眠不足へ連鎖すること。**
Rs 算出と Cascade 判定機能は Step 4 で実装するため、ここでは Event ログ上で連鎖の成立を確認する。

### Step 4: Event / 因果 / 指標
Event Engine、Causal Edge、Sleep Transmission、Rs、Cascade 判定。
Patient Zero から New Sleep-Deprived Case までの因果経路を、データ上で遡れる状態にする。

### Step 5: AI Decision
`AiDecisionGateway`、OpenRouter Adapter、Rule-based Fallback、HTTP Adapter、Decision Cache、Decision Trigger、
`POST /api/agents/decision`。詳細は [docs/実装計画.md](../実装計画.md)。

### Step 6: Watch Mode UI
`watch-mode-engine.composition`、City Map（Canvas）、Agent 可視化、再生制御。

### Step 7: 観測 UI
KPI パネル、Event Timeline、Agent Detail、Causal Graph（React Flow）。

### Step 8: 実験基盤
Experiment Runner、Baseline / Shock 比較、Experiment Dashboard。
比較実験では Population・Agent 属性・City 構造・Random Seed・初期交通量・基本 Simulation Parameter を固定し、
比較対象の Experimental Variable だけを変更する（要件定義 28 章）。

### Step 9: Multi-seed と介入
Multi-seed Runner（Quick 3 / Standard 10 / Final 10〜20 Seeds）、Intervention 4 種
（Mandatory Rest / Overtime Limit / Flexible Work / Remote Work）、Batch Experiment。
介入は効果だけでなく副作用（Accident Count、Commute Delay、Overtime）も測定対象とする。

### Step 10: Critical Point Explorer
初期睡眠不足率の自動 Sweep（1% / 3% / 5% / 7% / 10% / 15% / 20%）と Cascade Probability の算出・表示。

### Step 11: Sleep Super-spreader Explorer
Stage 1（Rule-based 高速 Simulation で全 Agent を Patient Zero 候補として評価）、
Stage 2（上位 10〜20 Agent を AI Decision 有効・複数 Seed で再評価）、ランキング表示。

### Step 12: Logistics 詳細化 / Simulation Replay
Logistics Hub → Delivery Worker → Store の連鎖を細分化する。
Replay は保存済み Event 列から Run を再構成し、City Map 上で再生する。

### Step 13: AI Model 比較
同一 Seed・同一都市条件で `AI_MODEL` のみ変更し（Gemma / Qwen / Llama）、Cascade 発生確率の差を比較する。

### Step 14: スケール拡張と自動分析レポート
500 Agent / 14 日 Simulation の性能検証、`experiment_results` からの自動分析レポート生成。

## 14. テスト方針

詳細は [docs/テストガイドライン.md](../テストガイドライン.md) と [docs/品質チェック・テスト規約.md](../品質チェック・テスト規約.md) に従う。本計画で特に重視するもの:

| 対象 | 種別 | 検証内容 |
|---|---|---|
| Sleep / Fatigue / Stress | Unit | 計算式と境界値（Sleep Debt = 1h / 2h / 5h） |
| 確率イベント | Unit | Seed 固定時に同一の抽選結果になる |
| Causal Edge | Unit | 時間的前後だけでは因果が生成されない |
| Rs / Cascade | Unit | Rs = 1.0、Cascade Reach = Population の 10% の境界 |
| Event 伝播 | Unit | `MAX_EVENT_DEPTH` で打ち切られ無限連鎖しない |
| Run 全体 | Unit | 同一 Seed・同一 Config で 2 回実行し KPI と Event 列が一致する |
| Prisma Repository | Integration | 保存後の DB 状態を検証する。エラー時に中途半端なデータが残らない |
| OpenRouter Adapter | Integration | Structured Output のパース、形式不正時の挙動 |
| Fallback | Integration | OpenRouter を常時失敗させても Run が完走する |

## 16. リスクと対応

| リスク | 影響 | 対応 |
|---|---|---|
| Watch Mode でブラウザが 300 Agent の描画に耐えられない | デモが成立しない | City Map を Canvas に統一し、低 Zoom 時はエリア単位で集約表示する。Tick 更新と描画フレームを分離する |
| Engine が domain 層からクライアントへ意図せず広く露出する | 依存ルールの形骸化 | 露出口を `watch-mode-engine.composition` の 1 ファイルに限定し、depcruise ルールは緩めない |
| AI 呼び出しコストが実験回数に比例して膨らむ | 実験が回せない | Decision Trigger 方式 + Decision Cache。Batch / Sweep / Stage 1 は Rule-based で実行する |
| Cascade が全く発生しない / 常に全域へ拡大する | 発見が得られない | 閾値と乗数を ExperimentConfig 化し、パラメータ調整を実装と分離する |
| 書き込み量が多く Batch Experiment が DB 律速になる | 大量実験ができない | 重要 Event のみ保存、Metrics のサンプリング、バルク Insert、同時実行数の制御 |
| 因果が「直前に起きた Event」で機械的に繋がれる | 結果の信頼性が失われる | 入力 Event ID の明示的な受け渡し経路からのみ CausalEdge を生成し、Unit テストで担保する |

### 実装中に判明した事実

- **Driver Shock は同率の Random Shock / Manager Shock より Cascade Reach が 4〜5 倍大きい。**
  300 Agent・7 日・5 Seed 平均で driver 27.0 / random 6.2 / manager 3.0 / baseline 4.8。
  運転職が Transportation Network 経由で不特定多数へ遅延を配る一方、Manager の伝播先は
  自分の部下に限られることが効いている。
- **初期睡眠不足率 5%〜7% の間で Cascade Reach が不連続に増える**（20.8 → 45.6、5 Seed 平均）。
  臨界領域の候補。
- **Cascade Probability は現状すべて 0%。** 要件定義 24 章の判定（Rs > 1 が 2 Generation 以上継続
  かつ Reach ≥ 10%）に対し、Generation 0 → 1 は爆発的だが Generation 1 → 2 で急速に減衰するため、
  Rs > 1 が 2 世代続かない。Cascade は「深く続く」より「一度大きく広がって収束する」形をとる。
  24 章の判定は変更せず、この形を取りこぼさないための補助指標を併記する:
  **Outbreak 発生率**（Rs の世代継続を問わず Reach が 10% へ達した Run の割合）と
  **収束世代**（Rs が閾値を超えたあと初めて閾値以下へ落ちた世代）。どちらも Experiment Dashboard の
  比較表と自動分析レポートに出る。過去に保存した実験には無いため、その場合は `-` を表示する。
- **Mandatory Rest が最も強く Cascade を抑える**（Reach 67.8 → 12.2、5 Seed 平均）。
  一方 Flexible Work は Reach を下げる（67.8 → 27.6）が Peak Rs は 6.50 まで跳ね上がっており、
  「平均を下げるが局所的な爆発は増やす」副作用が観測された。
- **Network の境界にいる Agent の伝播力が突出する。**
  300 Agent・3 日・Patient Zero 1 人での全 Agent 評価で、伝播が通過した Network 数別の
  平均伝播回数は 1 Network が 3.03（n=34）に対し **2 Network は 14.80（n=10）** と約 5 倍。
  職種別でも driver 3.17 / delivery_worker 2.20 / manager 0.90 / office_worker 0.29 /
  store_worker 0.00 と運転職が突出する。
- **Patient Zero の寄与は 4 日以上の Run では背景に埋もれる。**
  日数を伸ばすと通常の残業・スケジュールだけで自然発生する睡眠不足が増え、
  Patient Zero を変えても Run 全体の指標がほとんど動かなくなる
  （300 Agent・7 日では誰を起点にしても事故 28 件・新規ケース 7 件でほぼ一定）。
  そのため Super-spreader の比較は背景が静かな短い期間で行う必要がある。
