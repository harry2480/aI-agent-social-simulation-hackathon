## 概要（調査時点）

`apps/webapp/src/` と `apps/webapp/scripts/` 配下の全モジュールを調査し、コンポーネント・Hook・
Route Handler・Domain Service 内に埋め込まれた純粋関数（テスト可能なロジック）の候補を洗い出した。

本プロジェクトは `src/frontend/lib/` に表示ロジックを切り出す方針が既に確立しており、
そこに置かれた 9 ファイルはすべて Unit テスト済みである。一方で以下の 3 つの層に穴が残っている。

1. **Domain Service の直接テストが無い** — Simulation Engine 経由の間接テストのみで、
   閾値や倍率などの物理法則を単体で固定できていない
2. **描画・集計ロジックがコンポーネント内に閉じている** — Canvas 座標計算、Chart 系列変換、
   KPI 行の組み立てなど
3. **scripts/ に同一実装が 2 箇所ある** — `run-experiment.ts` と `compare-ai-models.ts` で
   集計関数がまるごと重複している

### 判明した「上限に到達しない」実装（整理済み）

`workFailureProbability` の `Math.min(0.4, ...)` は、`Fatigue` / `Stress` が `Agent` 側で
0〜100 にクランプされるため到達しなかった（最大 `0.002 × 6 × 2.5 = 0.03`）。
「作業ミスは最大 40% 起きうる」と読めてしまうため削除した。実際の上限 3% はテストで固定している。

同じ形をした `accidentProbability` の上限は、いったん `MAX_ACCIDENT_PROBABILITY_PER_TICK`
として名前を付けて残していた。`trafficLevel` が `ExperimentConfig.create` で
範囲検証されておらず（Settings 画面のみ 0〜3 に制限）、API やスクリプトから
任意の値が入りうる状態への対症療法だったため。

**対応済み（Issue #41）:** `trafficLevel` を含む 4 項目の範囲検証を `ExperimentConfig.create`
へ移し、Settings 画面はそれを呼ぶ形にした。`trafficLevel` が 3 以下に収まることで
事故確率も最大 11% にとどまり上限へ到達しなくなったため、`accidentProbability` の
クリップも削除した。実際の最大値はテストで固定している。

## 調査後に見つかった穴

Tier 分類の対象外（「既にテスト済み」と判断した）だが、Tier 1 完了後のカバレッジ計測で
`sleep-transmission.service.ts` が **83.0% で最下位**だったため追加で対応した。

| 未到達だった箇所 | 内容 |
|---|---|
| `deprivedPopulation` | 関数まるごと未呼び出し |
| `findUpstreamActor` の `visited` 判定 | 同じ Event へ複数経路で到達する場合 |
| `findUpstreamActor` の Event 未検出分岐 | 参照先が記録されていない場合 |
| `detect` の actor 未設定分岐 | 受け手を特定できない Event |

現在は行カバレッジ 100%・4 関数すべて到達。

**注意:** `visited` は因果が循環したときの無限ループを防いでいる。
これを外すと該当テストは「失敗」ではなく**ハング**する（同期ループのため
Vitest のタイムアウトでも止まらない）。`pnpm verify` が無反応になった場合はここを疑うこと。
